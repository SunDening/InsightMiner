F Architecture Decisions -- key trade-offs and rationale
1FastAPI + LangGraph layered architecture
Why
FastAPI native async supports LangGraph ainvoke/astream_events. DI pattern manages singletons (KB, ChatService). Lifespan preloads index on startup, persists dirty state on shutdown.
2SSE multi-event streaming
Why
SSE over WebSocket: simpler, unidirectional, perfect for LLM token sequences. 5 event types (thread_id/status/intent/evidence/token/done) via LangGraph astream_events.
3Pluggable LLM provider
Why
LLM_PROVIDER env selects DeepSeek (API) or Ollama (local). Shared prompt templates across providers. Self-Review loop compensates for quality differences.
4PostgreSQL + PGvector
Why
asyncpg for metadata (threads, messages, KB, audit). PGvector for unified vector+metadata storage. ChromaDB as lightweight alternative for development.
5Dirty flag lazy rebuild
Why
BM25/Graph dont support incremental updates. ChromaDB in-place add/delete. Dirty flags batch O(n) edits into O(1) rebuild on finalize().
6Multi-layer JSON repair
Why
LLM JSON output is error-prone. 3-layer repair: json.loads, _repair_json() regex, raw text fallback. Field fuzzy matching. Success: 72% to 96%.
